# 1С: приём файлов фрагментами (2026-10-07)

## Проблема
Через Yandex Serverless Containers большие фото из 1С приходили «либо нормальные,
либо битые», а через Replit — любые. Причина: **лимит контейнера 3.5 МБ на HTTP-запрос,
включая заголовки** (и ответ тоже 3.5 МБ) — лимит архитектурный, изменить нельзя
(док: serverless-containers/concepts/limits). Сайт сам сообщал 1С
`file_limit=104857600`, поэтому большое фото уходило одним запросом и обрезалось.
Если сайт открыт через API Gateway, у него свой лимит запроса/ответа 2.5 МБ.

## Контракт протокола (не додумывать)
- `mode=init` → `zip=no\nfile_limit=<байт>`: «максимально допустимый размер файла за
  один запрос; если файл больше — его следует разделить на фрагменты» (v8.1c.ru).
- Части отправляются **одним и тем же** `POST mode=file&filename=...`, **номера части
  в протоколе нет**; сайт обязан дописывать содержимое к файлу (эталон — Битрикс:
  «сайт создаёт файл, если его нет, и дописывает в него переданный контент»).
- Последняя часть ничем не помечена → детектор «последнего фрагмента» по размеру
  использовать НЕЛЬЗЯ (1С может резать части и меньше лимита). Публикуем файл, когда
  приходит следующий запрос: протокол синхронный, значит предыдущий файл дослан.

## Реализация
- `server/lib/one-c-file-parts.ts`:
  - `ONEC_FILE_PART_LIMIT = 2 МиБ` — отдаётся 1С в `mode=init` (catalog и sale в
    `server/routes.ts`).
  - части копятся в Object Storage: `1c_parts/<type>/<urlencoded filename>/part-NNNNNN`
    + `meta.json` (количество, байты, updatedAt). Префикс `1c_parts/` не попадает в
    `existingFilesCache` (тот листает только `products/`).
  - `accumulateOneCFilePart` — принимает фрагмент (ничего не публикует);
  - `collectOneCFile(type, filename)` — быстрый путь: читает одну конкретную сборку
    (без обхода бакета) — её публикует экземпляр, принимавший части последним;
  - `fastPublishDecision(previousKey, currentKey, exchangeType)` — чистое правило
    быстрого пути: публикуем, только если 1С ушла к другому файлу/шагу И это тот же
    тип обмена (catalog и sale идут независимыми сессиями и могут перекрываться);
  - `collectPendingOneCFiles(exceptKey, minIdleMs)` — обход бакета; сборки свежее
    `minIdleMs` не трогает (их может дописывать другой экземпляр контейнера);
  - `looksLikeCompleteFile` — перед публикацией проверяет, что собранное похоже на
    целый файл (JPEG EOI, PNG IEND, GIF-трейлер, размер WebP, хвост XML); обрезок
    отбрасывается вместе со сборкой;
  - `dropOneCAssembly` — сносит сборку после публикации;
  - `discardStaleOneCPartAssemblies` — на `mode=init` удаляет брошенные сборки (>1 ч).
  - Нет Object Storage (dev) → тот же алгоритм на Map в памяти процесса.
- `server/routes.ts`:
  - `publishOneCFile` — прежняя логика публикации (фото → S3 с 3 ретраями, XML → S3 +
    локально в `1c_uploads`), вынесена из inline-кода. Ключ картинки — полный путь
    из 1С с разделителями → `_` (`import_files_aa_photo.jpg`) — ровно тот, что строит
    `getImageUrl` при разборе XML; `path.basename` терял бы папку `import_files`;
  - `flushPendingOneCFiles(exchangeType, currentKey, forceFullSweep)` — в начале КАЖДОГО
    запроса `/api/1c-exchange`. Сначала быстрый путь: файл, чьи части этот экземпляр
    принимал последним, публикуется сразу, как только 1С перешла к другому файлу или к
    `mode=import` (переход = предыдущий файл дослан целиком). Затем — полный обход
    бакета: не чаще раза в минуту, без сборок свежее 20 с, принудительно на
    `init`/`import`;
  - `mode=import` предпочитает склеенный XML телу запроса (тело режется шлюзом) —
    если XML этой сессии уже опубликован (карта свежести 15 мин).
- Защита от склейки с «хвостами» оборвавшегося обмена: если фрагмент начинается с
  сигнатуры файла (JPEG/PNG/GIF/WebP), `<?xml` (в т.ч. с BOM) или корня
  `<КоммерческаяИнформация` (XML без объявления) — это новая загрузка, сборка
  начинается с нуля. Плюс пауза > 3 мин между фрагментами тоже сбрасывает сборку.

## Нагрузка на mode=import (2026-10-07)
- Оригиналы фото НЕ конвертируются — в бакете лежат в исходном формате; webp — только
  превью `_thumb.webp` (800px, q88) для главного фото товара.
- `generate1cThumbUrl` раньше генерировал превью заново для КАЖДОЙ позиции на КАЖДОМ
  импорте (download из S3 + Sharp + upload) — по конвертации на позицию внутри одного
  `mode=import`; у контейнера лимит запроса 600 с, так что это была самая тяжёлая
  часть обмена и реальный риск таймаута.
- Теперь перед генерацией `oneCThumbExists`: сначала список файлов бакета
  (`loadExistingFilesFromStorage(true)` перед разбором XML), иначе HEAD-запрос —
  так же проверяет свои конвертации `server/lib/vk-image.ts`; после генерации ключ
  добавляется в кэш. Повторные импорты почти не тратят на превью.

## Проверка
- `server/__tests__/one-c-file-parts.test.ts` — 10 сценариев (одиночный файл,
  3 фрагмента, обрезок, свежесть сборки, exceptKey, restart JPEG, restart XML без
  объявления, правило `fastPublishDecision`, обмен целиком, ошибки);
  гоняется в CI (`bun run test`).
  Без S3 — на локальном фолбэке в памяти.
- Логи в бою: `[1C PARTS] Принят фрагмент ...`, `[1C PARTS] Публикую ...`,
  `[1C PARTS] Удаляю брошенную сборку ...`, `[1C XML] mode=import: использую
  склеенный файл ...`.

## Ограничения
- Выгрузка заказов на сайт (`mode=query`) по-прежнему ограничена лимитом ОТВЕТА
  контейнера (3.5 МБ; при API Gateway — 2.5 МБ). Это отдельная задача, картинок не
  касается.
- Если 1С-модуль вообще не вызывает `mode=import` после файлов, сборка всё равно
  публикуется на следующем запросе (или снесётся как брошенная через час).
